# 0001. 전체 구조: 백엔드 분리 + 웹/모바일 클라이언트

- 상태: 채택
- 날짜: 2026-11-10

## 배경

만들 기능: 블로그 템플릿 저장 · 실제 블로그 연동 발행, 스케줄러, 할 일 관리, 원격 PC 제어, 자동화 스크립트.
**웹과 모바일 앱 둘 다**에서 사용하고, 앱을 닫아도 자동화는 계속 돌아가야 한다.

## 선택지

- **정적 사이트 (Astro 등)**: 가볍지만 스케줄러·자동화·원격 제어 불가 → 탈락
- **Next.js 풀스택 + 서버리스(Vercel)**: 간단하지만 항상 켜진 프로세스(스케줄러, WebSocket)가 어렵고 모바일 API 공유가 애매함 → 탈락
- **BaaS (Supabase/Firebase)만 사용**: DB·인증은 편하지만 자동화·원격 제어 로직을 둘 곳이 없음 → 탈락
- **백엔드 분리**: 서버 하나가 모든 일을 처리하고 웹·모바일은 화면 역할 → **채택**

## 결정

```
[웹 Next.js] [모바일 Expo] ──HTTP API──▶ [server] ◀──WebSocket──▶ [원격 PC agent]
                                          │
                                   [PostgreSQL]
```

- `server/`: API, 스케줄러, 자동화 실행, agent 연결의 중심
- `web/`: Next.js 대시보드 (화면만, 비즈니스 로직은 server에)
- `mobile/`: Expo. 처음엔 웹을 PWA로 쓰다가 필요할 때 추가
- `agent/`: 원격 PC에 설치하는 프로그램
- 배포: 24시간 켜진 머신(집 미니PC/NAS 또는 VPS) + Docker Compose, 외부 접속은 Tailscale

## 이유와 영향

- 원칙: **모든 일은 server가 하고, 클라이언트는 버튼과 화면만 담당한다.**
- 인증은 모바일을 고려해 토큰 기반으로 설계해야 한다. 원격 제어 기능이 있으므로 인증은 필수다.
- 블로그 자동 발행 가능 여부는 플랫폼에 달렸다 (WordPress/Ghost는 API 가능, 티스토리 Open API 종료, 네이버는 글쓰기 API 없음 → 브라우저 자동화 필요). **아직 플랫폼 미정.**

## 폴더 이름: `backend/` + `frontend/` 대신 `server/` + `web/` (추가: 2026-11-10)

"보통은 backend/frontend로 나누지 않나?"라는 질문에 따라 이름을 정한 근거를 남긴다. 구조(백엔드 분리)는 같고 **이름만 다르다.**

| 방식 | 예시 | 어울리는 경우 |
|---|---|---|
| 역할(앞/뒤)로 이름 짓기 | `backend/`, `frontend/` | 화면이 웹 하나뿐. 가장 흔하고 직관적임 |
| **무엇인지로 이름 짓기** | `server/`, `web/`, `mobile/`, `agent/` | 클라이언트가 여러 개. 백엔드 언어가 다름 |
| JS 모노레포 | `apps/{api,web,mobile}` + `packages/` | 전부 TypeScript이고 공유 코드가 많음 (Turborepo/Nx/pnpm) |

**결정: `server/`, `web/` (나중에 `mobile/`, `agent/`)을 유지한다.**

- 모바일 앱도 프론트엔드라서, `frontend/`라는 이름은 모바일이 생기는 순간 애매해진다.
- 백엔드가 Python이라 `apps/` + `packages/` 모노레포의 장점(TS 코드와 타입 공유, Turborepo 빌드)이 작다. 타입은 OpenAPI 생성으로 맞춘다.
- 나중에 웹과 모바일이 공유할 TS 코드가 많아지면 `apps/` + `packages/`로 옮기는 것을 다시 검토한다. 폴더 이동이라 비용이 작다.
